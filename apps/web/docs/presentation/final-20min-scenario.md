## 04. 브라우저 보호에 공통 DNS 정책을 더합니다 — 02:20–03:35

*상태: reference · 화면 id: `friction-barriers`*

[화면] 브라우저, 추가 앱, 보호 DNS의 적용 조건을 차례로 선택합니다.

[발표] Chrome에는 Safe Browsing 표준 보호가 기본으로 켜져 있습니다. 저희는 기존 브라우저 보호가 켜진 상태에서 공통 DNS 정책을 더하는 접근을 택했습니다.

브라우저는 방문 URL을 검사하고, 별도 보안 앱은 각자의 기능과 권한에 따라 동작합니다. 보호 DNS는 그 서버로 들어오는 이름 조회에 공통 정책을 적용합니다. 예를 들어 login-alert.test의 /account 페이지를 열면 DNS의 질의 대상은 login-alert.test라는 호스트 이름까지입니다. /account 경로는 브라우저·HTTP 계층의 검토 대상입니다.

이 차이 때문에 여러 앱에 정책을 적용할 수 있는 장점과 같은 호스트 안의 정상·악성 경로를 구분하기 어려운 제약이 함께 생깁니다. 위협정보가 갱신되기 전의 공백도 남습니다. 추가 효과는 동일한 브라우저 보호 설정에서 따로 비교해야 합니다.

[전환] 이런 네트워크 보호 방식에는 이미 운영 선례가 있습니다.

## 05. 운영 선례를 바탕으로 정책 집행의 경계를 검증합니다 — 03:35–04:15

*상태: reference · 화면 id: `precedents`*

[발표] 영국 NCSC는 공공부문용 Protective DNS를 운영하고, 국내 KISA는 자체 DNS를 운영하는 기관을 위한 싱크홀 서비스를 제공합니다.

저희는 이 선례를 바탕으로 작은 실험 환경을 구성했습니다. 기여는 외부 위협정보를 승인 가능한 정책으로 만들고, 서명 배포와 집행·철회를 하나의 실행 흐름으로 연결한 데 있습니다.

[전환] 먼저 승인된 정책이 DNS 응답에 어떻게 쓰이는지 보겠습니다.

## 06. 새 이름 조회에 승인된 차단 정책을 적용합니다 — 04:15–06:05

*상태: implemented · 화면 id: `dns`*

[화면] 정상 조회와 차단 대상 조회를 직접 선택해 질의·응답 방향을 보여 줍니다. 선택한 사례는 1초간 쉰 뒤 반복하며, 다른 사례는 사용자가 직접 선택합니다.

[발표] 단말은 웹 서버에 새로 연결할 주소를 얻기 위해 DNS에 이름을 질의합니다. 보호 DNS는 미리 내려받아 검증한 정책과 그 이름을 대조합니다.

현재 설치 구성에서는 승인된 BLOCK 범위 밖의 이름을 업스트림 DNS로 전달합니다. 이 구현의 로컬 응답 캐시는 꺼져 있어 같은 이름의 재조회도 업스트림으로 나갑니다. 차단 목록은 로컬에서 대조합니다. 원격 위협정보 조회는 후보 수집과 정책 준비 단계에서 수행합니다.

승인된 BLOCK 범위에 해당하면 NXDOMAIN, 즉 해당 이름이 없다는 응답을 돌려줍니다. 이 새 조회로 목적지 주소를 얻는 경로가 중단됩니다. 이미 단말에 남은 주소나 기존 연결은 별도의 경계입니다.

여기서 정책을 내려받는 통신과 사용자의 이름 조회를 분리한 것이 핵심입니다. 정책 공급 서버는 서명 정책을 제공하고, 보호 DNS는 그 정책을 새 이름 조회에 적용합니다.

[전환] 그렇다면 DNS가 따르는 차단 목록은 누가, 어떤 근거로 만들까요?

## 07. 후보를 검토하고 승인된 정책만 배포합니다 — 06:05–08:10

*상태: implemented · 화면 id: `architecture`*

[화면] 현재 코드 탭에서 네 단계를 따라갑니다. 공공·ISP 탭은 확장 제안에서 다룹니다.

[발표] 외부 피드에서 찾은 URL은 먼저 후보로 보관합니다. OpenPhish는 URL 후보를 제공하고, Safe Browsing API는 지정한 URL에 알려진 위협 근거가 있는지 조회합니다. 빈 결과는 해당 조회에서 반환된 위협 근거가 0건이라는 뜻입니다. 사이트의 안전성은 추가 근거로 검토합니다.

다음은 관리자 검토입니다. 같은 호스트에 정상 서비스가 함께 있을 수 있으므로, 관리자는 하위 서비스 영향까지 확인해 실제 차단 범위를 별도로 승인합니다. 점수 엔진은 호스트 단위의 EXACT 제안을 내지만, 현재 dnsmasq는 하위 이름까지 포함하는 SUBTREE를 집행합니다. EXACT 입력은 거부하며, 하위 서비스 영향까지 승인한 별도 정책이 필요합니다.

로컬 관제에는 위협정보 갱신과 검토가 연결돼 있습니다. 클라우드 관제는 별도 수집기의 검증 결과를 가져와 검토·초안을 작성합니다. 서명은 외부에서 수행하고, 관리자 CLI나 인증된 클라우드 관제에서 검증해 게시합니다. DNS 노드는 게시된 정책을 주기적으로 받아 적용하므로, 게시 성공과 실제 적용은 따로 확인합니다. 여덟 기준 위험 점수는 수동 보조 제안으로 사용합니다.

마지막으로 DNS가 서명, 대상 장치, 순서와 만료를 검증합니다. 서명은 발행자와 변조 여부를 확인합니다. 내용의 정확성은 근거 검토와 별도의 평가로 확보해야 합니다.

## 11. HTTPS에서는 차단과 사유 안내가 분리됩니다 — 14:15–16:20

*상태: known-limit · 화면 id: `http`*

[화면] HTTP 흐름을 보여 준 뒤 HTTPS 흐름으로 전환합니다.

[발표] HTTPS에서도 목적지의 새 이름 조회를 차단할 수 있습니다. 어려운 부분은 차단된 사용자를 제3자의 HTTPS 안내 페이지로 자연스럽게 전환하는 것입니다.

통제된 평문 HTTP 실험에서는 DNS가 안내 서버 주소를 주고, HTTP 서버가 302 응답으로 안내 페이지에 보냈습니다. DNS 응답과 HTTP 리다이렉트는 서로 다른 단계입니다.

HTTPS는 HTTP 응답을 읽기 전에 원래 접속하려던 호스트의 TLS 신원 검증을 수행합니다. 안내 서버도 원래 호스트의 신뢰된 인증서를 제시해야 HTTP 응답까지 진행할 수 있습니다.

차단 이유를 전달하는 경로로 RFC 8914의 EDE 15, Blocked를 검토했습니다. 이는 DNS에 사유 정보를 담는 표준입니다. 사용자가 볼 안내를 만들려면 리졸버와 브라우저·OS의 지원을 연결해야 하며, 현재 프로토타입의 후속 항목입니다.

[전환] 사유 안내와 별개로, 보호 정책을 거치지 않는 접속 경로도 남습니다.

## 12. 보호 범위는 선택한 DNS 경로까지입니다 — 16:20–17:50

*상태: proposal · 화면 id: `topology-public`*

[화면] 보호 DNS 경로와 대체 리졸버 경로를 비교합니다. ISP·공공 구성은 제안임을 말합니다.

[발표] DNS 보호는 실제 질의가 어느 리졸버로 가는지에 달려 있습니다. 외부 DNS나 VPN의 리졸버, 다른 네트워크를 사용하면 이 로컬 정책을 거치지 않을 수 있습니다. 직접 IP 연결과 기존 캐시·연결도 별도로 봐야 합니다.

DoH는 DNS의 전송 방식입니다. 보호 정책을 집행하는 리졸버로 연결하면 DoH에서도 정책을 적용할 수 있습니다. 우회 여부는 선택된 리졸버의 정책 집행 여부로 판단합니다.

참여 ISP가 보호 DNS를 운영하면 그 경로를 선택한 가입자까지 적용 범위를 넓힐 수 있습니다. 이 단계에는 이용자 선택, 최소한의 로그, 피드의 이용·갱신 조건, 이의신청과 철회 책임이 필요합니다. 대체 리졸버·VPN·다른 네트워크 경로는 참여 ISP의 보호 범위와 별도로 평가해야 합니다.

269는 10월 30일 OpenPhish 후보 호스트의 팀 실행 기록입니다. GSB의 1개 테스트 호스트·2개 위협 근거도 팀 기록이며, 원본 API 응답·요청 시각·해시 인수가 필요합니다. 이 수치는 팀의 수집·연결 기록으로 구분하며, 성능 평가는 독립된 시험 자료로 수행해야 합니다.

240/240은 11월 4일 실험 호스트에서 f1977cce 기반 코드를 사용한 비특권 루프백 합성 DNS 실험입니다. `3회 × 4상태 × 5이름 × A/AAAA × UDP/TCP`의 기대 응답 일치이며 보호 공백과 과차단 반례를 포함합니다. 검증 범위는 해당 고정 커밋과 합성 질의 조건입니다. 최신 main 및 실제 위협 탐지 성능은 별도 검증이 필요합니다. ## 화면에서 버튼을 누르면 실제 DNS가 바뀌나요?

발표 화면은 설명용 상태 전환입니다. 실제 기능의 근거는 격리 DNS 실험 기록이고, 실제 지연은 CSV 측정 기록입니다. 발표 애니메이션은 브라우저 안의 설명용 표현이며, 운영 DNS 적용과 최신 노드 상태는 관제·실측 기록으로 확인합니다. 운영 관제 코드는 별도로 구현돼 있습니다. 서명은 외부에서 수행하고, 게시·검증은 관리자 CLI 또는 인증된 클라우드 관제에서 처리합니다. 게시 성공과 실제 DNS 적용은 따로 확인합니다.

## EXACT와 SUBTREE 차이는 어떻게 처리하나요?

점수 엔진의 EXACT는 특정 호스트에 대한 제안입니다. 현재 dnsmasq 정책 입력은 SUBTREE만 허용하고 EXACT를 받으면 거부합니다. 관리자는 하위 서비스 영향까지 검토한 별도 SUBTREE 승인을 해야 합니다. 현재 계약에서는 부모 BLOCK의 하위 범위를 함께 집행합니다. 자식 ALLOW 예외 기능은 현재 지원 범위 밖입니다. 정상 서비스 영향이 확인되면 부모 차단 범위를 재검토하거나 철회합니다. [정책 계약 코드](https://github.com/youngjinphys/SKT-ALEPH-bsB-E-Capstone/blob/6bf8ccac6069771811ca0e75c9c1183e004c392c/apps/dns-agent/src/dns_agent/policy.py)

## CNAME, 정상 사이트 내부의 악성 경로는 해결됐나요?

현재 CNAME 응답 체인의 차단 대상 처리는 보호 공백으로 남습니다. 위험 점수에서 CNAME 관련 근거를 쓰는 것과 DNS 응답 체인을 집행하는 것은 다른 기능입니다. DNS 이름 조회의 관측 단위는 호스트입니다. 같은 호스트의 정상·악성 URL 경로 판정에는 URL 수준의 관측이 필요합니다. 전자는 응답 체인을 다루는 구현의 개선 과제이고, 후자는 URL 수준 보호와 사이트 복구가 필요한 적용 경계입니다.

## 잘못된 갱신이나 만료는 모두 직전 정책 유지인가요?

잘못된 새 입력은 거부하되 기존 정책도 자기 유효기간까지만 사용합니다. 유효기간이 끝난 BLOCK은 에이전트 재평가에서 제거하고 일반 전달을 유지하도록 설계되어 있습니다. 안전한 정리·복구가 실패하면 중단하는 분기도 있습니다. 기존 정책의 사용 범위도 원래 유효기간으로 제한합니다. 서명은 발행자·무결성 확인에 사용하고, 정책 내용의 정확성은 별도 근거 검토로 확보합니다. [현재 만료·복구 처리](https://github.com/youngjinphys/SKT-ALEPH-bsB-E-Capstone/blob/6bf8ccac6069771811ca0e75c9c1183e004c392c/apps/dns-agent/src/dns_agent/transaction.py)

## 철회하면 바로 모든 단말이 복구되나요?

철회 정책의 게시·수신·적용이 끝나면 보호 DNS의 새 응답을 복원합니다. 이용자의 접속은 단말의 양성·음성 DNS 캐시, 재질의와 기존 연결에 영향을 받습니다. 사용자 복구 시간은 정책 전달과 단말 상태를 함께 측정해야 합니다. 실단말 종단 간 시간은 후속 검증 항목입니다.

## Pi의 1.75ms, 43.29ms, 49.44ms는 어떻게 읽나요?

반복 이름 조건의 직접 업스트림 p50은 약 43.29ms, Pi 전달은 약 49.44ms입니다. 이는 같은 CSV의 선형보간 분포 요약입니다. 운영 :53은 `cache-size=0`이고 측정 당시 `address=` 차단 줄이 없었습니다. 약 1.75ms는 같은 호스트의 임시 :55353에서 캐시를 켠 별도 히트 실험의 p50입니다. 이 값의 적용 범위는 임시 캐시 실험입니다. 운영 DNS의 차단 성능과 정책 추가 비용은 별도 통제 실험으로 측정해야 합니다.

원시 446행 중 준비·자가시험 6행을 제외했으며 그 안에는 timeout 2행이 있습니다. 분석한 440행은 성공했지만 한 클라이언트·한 LAN·UDP A의 한정된 표본입니다. 이 성공률은 해당 질의 표본의 응답 완료율입니다. 장기 가용성과 피싱 탐지율은 각각 별도 자료로 평가해야 합니다.

발표의 p50/p95는 정렬값의 `(n−1)p` 위치에서 선형보간했습니다. 기존 실행 문서는 nearest-rank를 사용하므로 약간의 수치 차이가 있습니다. 예를 들어 로컬−직접 40쌍의 중앙값은 선형보간 4.731ms, nearest-rank 4.701ms이며, 두 arm의 p50을 먼저 구한 차이 6.159ms와도 다릅니다. 짝별 차이의 중앙값과 조건별 중앙값의 차이는 각각의 산식으로 구분해 보고합니다. [원시 CSV](https://github.com/youngjinphys/SKT-ALEPH-bsB-E-Capstone/blob/6bf8ccac6069771811ca0e75c9c1183e004c392c/docs/review/dns-latency-arms-20261103.csv) · [실행 조건](https://github.com/youngjinphys/SKT-ALEPH-bsB-E-Capstone/blob/6bf8ccac6069771811ca0e75c9c1183e004c392c/docs/review/dns-latency-arms-20261103.md)

## HTTPS는 차단할 수 없다는 뜻인가요? EDE가 경고 화면을 만드나요?

HTTPS 목적지도 새 DNS 조회에서 차단할 수 있습니다. 제약은 DNS 응답만 바꿔 원래 호스트의 신뢰된 인증서 없이 제3자 안내 서버로 전환하는 데 있습니다. RFC 8914 EDE 15는 차단 사유 메타데이터입니다. 사용자 경고 화면으로 연결하려면 지원 클라이언트와의 구현·검증이 필요합니다. SDE는 2026-11-03 확인 시 RFC Editor Queue에 있는 Internet-Draft입니다. [RFC 9525](https://www.rfc-editor.org/rfc/rfc9525.html) · [RFC 8914](https://www.rfc-editor.org/rfc/rfc8914.html) · [SDE 상태](https://datatracker.ietf.org/doc/draft-ietf-dnsop-structured-dns-error/)

## DoH를 쓰면 무조건 우회하나요? DNS에서 HTTPS 헤더도 볼 수 있나요?

DoH는 DNS를 HTTPS로 운반하는 방식입니다. 보호 정책을 집행하는 리졸버를 선택하면 같은 정책을 적용할 수 있습니다. 다른 리졸버·VPN·다른 네트워크로 나가면 로컬 정책을 거치지 않을 수 있습니다. 이 DNS 프로토타입의 관측 범위는 질의된 호스트 이름입니다. HTTPS 헤더와 URL 경로 판정에는 브라우저·단말·별도 프록시 등 추가 관측 지점이 필요합니다. [RFC 8484](https://www.rfc-editor.org/rfc/rfc8484.html)

## 수집과 배포는 자동인가요? 관제에서 어디까지 할 수 있나요?

로컬 후보 수집과 이미 게시된 정책의 DNS 수신·적용에는 주기 실행 경로가 있습니다. 로컬 관제의 갱신 worker와 달리, 통합 HEAD9e84275의 클라우드 관제는 자동 수집이 미구성이며 검증 결과 파일을 가져옵니다. 클라우드에서는 후보 검토·미서명 초안 작성 후 외부에서 서명한 envelope를 인증된 운영자가 검증·게시할 수 있습니다. 초안과 게시 API는 같은 운영자 인증 체계이며 서명 개인키는 외부 서명 환경에서 관리합니다. 게시 응답은 정책 게시 결과입니다. 실제 DNS 적용은 노드 보고로, LAN 단말의 보호는 단말별 질의로 추가 확인해야 합니다. ## 다음 실험의 성공 기준은 무엇인가요?

독립적인 악성·정상 판정 자료에서 동일 시점·브라우저 버전·보호 설정을 고정하고 DNS 적용 전후의 실제 차단과 정상 서비스 영향을 함께 비교합니다. 위협 URL을 여러 개 포함한 한 도메인을 독립 표본 여러 개처럼 세지 않도록 URL·호스트·캠페인 단위를 기록합니다. 정상 사이트의 일부 경로·공유 호스트, CNAME, 하위 서비스와 단말 캐시도 포함합니다. 이후 정책 게시부터 실단말 복구까지의 시간, 동일 Pi의 정책 전후·부하별 지연·완료 QPS·CPU/RAM을 측정합니다. 추가 차단만 늘고 오탐이나 복구 비용이 커진다면 설계를 다시 검토해야 합니다.
