# ADR-0001: 단일 Monorepo, 모듈별 독립 실행·배포

- **결정 상태:** 저장소 구조 기준선으로 채택. 기술 엔진/운영 API/암호화 구현은 팀 협의 대기.
- **적용 범위:** SKT ALEPH E조 Capstone. 최종 제출 정본은 `youngjinphys/SKT-ALEPH-bsB-E-Capstone`의 `main`.
- **결정일:** 2026-10-24

## 배경
발표 계획일은 2026-11-05입니다. IOC 수집·판정, 관리 대상 로컬 DNS 적용과 사용자용 별도 HTTPS 안내 포털을 병렬 개발합니다. 정책 계약과 통합 시연 커밋을 한 번에 추적할 필요가 있습니다.

## 결정
1. `apps/policy-server/`, `apps/dns-agent/`, `apps/warning-portal/`의 코드는 한 저장소에 두되 프로세스·배포 환경·인증·권한을 결합하지 않습니다.
2. `packages/policy-contract/`에는 버전된 데이터 형식과 양측 계약 검증 자료를 둡니다. Python 런타임 구현 코드를 서버와 DNS 에이전트가 직접 import하지 않습니다.
3. M1 격리 DNS 검증은 원격 서버·중앙 DB 없이 로컬 정책 JSON만으로 시작할 수 있습니다. M3 통합 시 원격 갱신 경로를 추가합니다.
4. DNS 엔진(Unbound RPZ 권고 후보), 응답 종류, 배포 인증, 정책 서명, AI 모델, 중앙 DBMS의 **구현 여부와 최종 채택은 별개**입니다.
5. HTTPS 포털은 독립적인 정상 TLS 오리진입니다. NXDOMAIN으로 차단한 피싱 사이트의 원래 HTTPS 탭을 안내 HTML로 자동 치환하지 않습니다.

## 대안 및 선택 이유
- **저장소 3개:** 모듈별 Git 접근 제어는 용이하지만 제출·정책 스키마·동작 시연의 교차 버전 추적 부담이 현재 일정에 비해 큽니다.
- **저장소 1개/단일 배포:** 형식은 단순하나 DNS 리졸버의 권한을 원격 웹서비스/프론트엔드와 결합하므로 채택하지 않습니다.
- **현재 선택:** 저장소 1개, 별도의 배포물 3개, 공통 데이터 계약 1개.

## 운영·검증 경계
- Git 접근권한으로 서비스 운영 권한을 부여하지 않습니다. 서비스마다 최소 자격증명과 별도 배포 경로를 사용합니다.
- 초기 CI는 파일 구성 및 위험 파일명만 검사하며 **DNS 차단·철회·서명·모델 성능은 검증하지 않습니다**.
- 실제 완료 여부는 각 모듈의 코드 SHA·실행 로그·격리 시험·담당자 검토로 증명합니다.
- 팀별 GitHub 계정이 확인되지 않았으므로 `CODEOWNERS`는 임의로 생성하지 않습니다.

## 재검토 조건
관리 권한이 다른 조직으로 분리되거나, 릴리스 주기가 완전히 달라지거나, 외부 제품으로 에이전트가 재사용된다면 저장소 분할을 재평가합니다. 그때도 공통 정책 데이터 계약은 독립 버전으로 관리합니다.
