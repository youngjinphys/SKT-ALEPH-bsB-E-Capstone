# 사설 DNS 레이턴시 측정 — 2026-11-03

이 문서는 비교군을 맞추기 전의 1차 측정이다. 같은 질의 이름을 맞춘 후속 결과는 [dns-latency-arms-20261103.md](dns-latency-arms-20261103.md)에 있다.

측정 시각은 2026-11-03 14:57 KST(05:57 UTC)이다. 클라이언트는 DNS 서버와 같은 LAN의 이 PC이고, 대상은 `192.168.7.69:53`이다. 설치본과 저장소 HEAD는 `9187102d8690ab580de79eb164cf4cc97bc34bad`이다.

원본 표본은 [dns-latency-20261103.csv](dns-latency-20261103.csv)에 있다. 각 계열은 워밍업 5회를 제외한 50회다. `elapsed_ms`는 질의 패킷을 보낸 뒤 응답을 받을 때까지의 클라이언트 왕복 시간이며, 서버 내부 처리 시간만 분리한 값은 아니다.

## 설치

로컬 `main`과 DNS 서버 체크아웃 모두 `git fetch` 이후 `origin/main`과 같은 커밋이었다. DNS 엔진 `/opt/aleph-dns/src`는 저장소 `apps/dns-agent/src`와 해시가 같아 `system_dns.py upgrade`는 실행하지 않았고, `aleph-dns`는 중단하지 않았다.

`/opt/aleph-policy-code`에는 정책 서버 모듈과 `aleph_policy_sync/telemetry.py`가 없었다. 기존 파일의 해시는 저장소와 같았다. fetch/apply 타이머만 잠시 멈추고 `scripts/deploy/upgrade-policy-runtime.sh --role dns --apply`로 코드 29개를 교체했다. 교체 후 설치본과 저장소 해시는 일치했다. 이전 코드는 `/opt/.aleph-policy-code.rollback`에 남아 있다. 키·정책·`/var/lib` 상태는 이 업그레이드가 바꾸지 않는다. 타이머는 다시 활성 상태다.

`aleph-ops-collect`와 `aleph-ops-send` 유닛은 서버에 없다. 텔레메트리 설치는 별도의 장치 키와 보고 URL이 필요하므로 이번 코드 교체에 포함하지 않았다.

측정 중 적용 정책은 `google.com` BLOCK SUBTREE 하나였고, 만료 시각은 2026-11-03 15:08 KST다.

## 결과

성공은 기대한 DNS 응답 코드를 시간 초과 없이 받은 경우다. 차단 계열의 기대값은 NXDOMAIN, 그 외는 NOERROR다.

고유 이름 50개는 모두 NOERROR이고 응답 레코드 수는 0이다. `example.org`의 없는 하위 이름은 이 경로에서 NXDOMAIN이 아니라 NODATA로 돌아왔다.

`google.com`과 `www.google.com`은 50회 모두 NXDOMAIN이었다. 중앙값은 1ms 미만으로, 같은 시각의 허용 질의 중앙값 약 43–51ms보다 짧다. 차단 응답은 로컬 정책에서 끝난다.

TCP `example.org` A는 50회 모두 NOERROR였다. 중앙값은 55.233ms이고, 그중 14회는 330–348ms에 몰려 p95가 343.768ms가 됐다.

같은 PC에서 Quad9(`9.9.9.9`)로 보낸 `example.org` A UDP 중앙값은 43.352ms다. 이 값은 경로가 다르므로 ALEPH 서버의 우열을 뜻하지 않는다.

## 한계

- 표본은 한 차례, 한 클라이언트, 한 LAN 경로다.
- 반복된 `example.org`은 리졸버 캐시 영향이 있다. 고유 이름은 질의마다 다르며 응답 레코드는 없었다.
- 차단 수치는 위 정책이 유효한 동안의 값이다. 15:08 KST 이후에는 같은 이름으로 재현되지 않는다.
- 업스트림 장애, 재부팅, IPv6 경로, DoH/VPN, 동시 사용자는 측정하지 않았다.
