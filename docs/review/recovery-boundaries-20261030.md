# 정책 캐시·게시 복구의 신뢰 경계 재검토

검토 기준: `08f3880fcfd3ed2e75b2aa4ee68375c37806e40e` (2026-10-30).
이 문서는 실제 재현한 결함과 남겨 둔 안전 경계를 구분합니다. 운영 서버를 변경하지 않았습니다.

## 이전 조치의 평가

서명/장치/시퀀스/만료 검증, DNS 상태 재확인, 적용 전 저널 및 원격 게시 완료 영수증은 필요한 조치입니다.
그러나 캐시와 보안 기록을 같은 종류의 상태로 취급하거나, 이미 완료된 작업을 재승인하려 하면
보안 검증을 지키면서도 정상 갱신이 불필요하게 멈출 수 있습니다.

| 경계 | 기준 코드에서 재현한 결과 | 수정 |
| --- | --- | --- |
| HTTP 메타데이터 형식 손상 | 정상 서명된 새 정책을 내려받기도 전에 계속 실패 | 안전한 소유권·크기 검사 후 JSON/필드 손상만 폐기 가능한 캐시로 처리 |
| HTTP 메타데이터 유실·해시 불일치 | 아직 검증 가능한 `current.json`이 있어도 다운로드 단계의 낮은 시퀀스/같은 시퀀스 충돌 검사를 생략 | 서명 정책의 신뢰 판단과 ETag 사용 여부를 분리 |
| 원격 게시·완료 영수증 기록 성공 후 저널 삭제 실패 | 옛 키 폐기 후 정리 작업도 이전 키에 의존해 실패 | 전체 envelope와 root 완료 영수증이 일치할 때만 정리; 재게시·만료 연장 없음 |

캐시 단계에서 이전 정책을 덮어쓸 수 있었다는 사실이 **곧 root DNS의 롤백 방어까지 우회됐다는 뜻은 아닙니다.**
root 적용의 독립적인 시퀀스 검사는 그대로 존재합니다. 이번 수정은 다운로드 계층의 검증 손실과 가용성 문제를 해결합니다.

## 복구 가능한 데이터와 복구해서는 안 되는 데이터

- `fetch-state.json`: 다운로드 최적화를 위한 HTTP 메타데이터입니다. 안전하게 읽은 2 KiB 이내 JSON/필드 형식 손상은 조건부 요청 없이 재수신합니다. 새 응답의 서명·장치·만료·시퀀스 검사는 생략하지 않습니다.
- `current.json`: 메타데이터가 없어도 서명이 현재 신뢰 키로 검증되면 다운로드 순서 비교의 근거로 유지합니다. 기존 키가 폐기된 경우에는 그 캐시로 새 응답을 인증하지 않습니다.
- `applied.json`, `pending-apply.json`, `.publication.json`, `.pending-publication.json`: 실행·승인 이력입니다. 이번 변경은 이 파일들의 손상을 무시하거나 초기화하지 않습니다.
- 원격 게시의 완료 영수증은 root가 이전에 서명을 검증하고 기록한 **로컬 완료 증거**입니다. 이미 기록된 동일 게시물의 저널을 제거하는 데만 사용합니다. 새 후보를 승인하거나 폐기된 키를 다시 신뢰하는 용도가 아닙니다.

## 검증 방법과 실제 범위

변경 전 GitHub blob과 바이트 단위로 동일한 핵심 모듈을 로컬에 복원해 먼저 실패를 재현했습니다.
이후 신규 회귀시험 **13개**(비특권 캐시 7개, root 게시 복구 6개)를 로컬에서 실행했습니다.
Ed25519 키 생성·서명·검증, 파일 권한·원자적 저장은 실제 동작입니다. 신규 캐시 시험의 HTTP 전송만 가짜 응답으로 대체했고,
게시 복구는 임시 디렉터리의 실제 파일 쓰기와 정리 오류 주입을 사용했습니다. 실제 DNS·NGINX를 구동한 시험이라고 주장하지 않습니다.

CI는 새 캐시 시험을 비특권 계정으로 명시적으로 실행하고, 게시 복구 시험을 별도의 root 단계에서 실행합니다.
기존 실제 localhost TLS, 네이티브 dnsmasq 및 nftables 시험 결과는 **해당 커밋의 Actions 로그**로 확인해야 합니다.

## 안전성 때문에 자동화하지 않은 경우

미완료 DNS 적용 기록과 이전 정책이 모두 만료되면, 현재 `attest`가 그 상태를 확인하지 못해
새 정책 적용이 멈출 수 있습니다. 별도 오류 주입에서 이 경계를 재현했습니다. root 적용 저널을 무조건 지우거나
만료된 정책을 다시 적용하면 실제 적용 여부가 불분명한 상태에서 이력을 잃을 수 있으므로 그렇게 수정하지 않았습니다.
운영자는 **inbox의 원본 서명 파일, root 적용 기록, DNS 정책 파일·상태·서비스 로그를 보존**하고 인수된 복구 절차로 처리해야 합니다.

이는 이번에 해결한 원격 게시자의 **완료 영수증이 이미 확정된** 경우와 다릅니다. 전자의 자동 복구를 운영 요건으로 삼으려면
만료된 상태의 읽기 전용 증명과 새 정책 게시를 하나의 명확한 복구 계약으로 설계·검증해야 합니다.

## 여전히 필요한 운영 검증

실제 두 서버의 TLS/키 배포→위협정보 검토→서명→LAN DNS 적용·철회, 주기적 정책 만료와 검토 인력의 가용성,
CNAME·HTTPS/SVCB·암호화 DNS·VPN·IPv6 우회, DNSSEC, 정상 하위 도메인의 과차단, 장애 중 서비스 가용성은 별도입니다.
테스트 개수나 서명 성공을 피싱 탐지율·실제 피해 예방률로 환산하지 않습니다.

## 외부 규격과의 관계

- [RFC 9111 §4.3](https://www.rfc-editor.org/rfc/rfc9111.html#section-4.3): ETag/304는 HTTP 응답 재사용의 검증입니다. 애플리케이션의 서명키 신뢰·정책 만료를 대체하지 않습니다.
- [TUF metadata 설명](https://theupdateframework.io/docs/metadata/): 서명·만료·이전 메타데이터와의 관계가 각각 필요하다는 설계 참고 자료입니다. 이 프로젝트의 단일 서명 포맷은 **TUF 구현이나 TUF 수준의 보장을 주장하지 않습니다.**
