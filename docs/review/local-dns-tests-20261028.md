# DNS 실행 및 장애 검토 (2026-10-28)

기준 소스는 `17d41c71f9ea3e42d2862bdb61717d885b8a6199`이며,
이 문서와 함께 적용된 변경을 별도로 검증했다.

## 발견 및 조치

- 실제 루프백 소켓으로 UDP는 정상 응답하고 TCP는 연결이 거부되는 상황을
  구성했다. 이전 주기적 건강 검사는 UDP만 검사하여 정상으로 판정했다.
  주기적 검사에 TCP A/AAAA 및 차단 카나리 검사를 추가하고 같은 반례를
  회귀 시험으로 남겼다. TCP 프레임의 분할 수신도 실제 소켓으로 시험했다.
- 설치 명령의 Python 버전과 systemd 서비스가 실행하는 `/usr/bin/python3`의
  버전은 다를 수 있다. 설치 및 업그레이드가 시스템을 변경하기 전에 실제
  서비스 인터프리터가 3.11 이상인지 확인한다. 미지원 버전·실행 실패·시간
  초과는 테스트에서 모의했으며, 실제 구버전 서비스 장애를 재현한 것은 아니다.

## 실행 환경과 결과

Ubuntu 24.04 컨테이너에서 PID 1은 systemd가 아니다. 네트워크 관리와
네임스페이스 권한이 없고 AF_NETLINK 소켓 생성은 `EPERM`으로 거부된다.
따라서 systemd 설치·재부팅·실제 nftables·LAN 포트 53은 시험하지 못했다.

별도로 빌드한 dnsmasq 소스 `cf08eeee12b0f76a1259736c7795bfae82e08d2c`
(버전 문자열 `UNKNOWN`, 배포판 패키지 아님)에 생성된 설정을 전달했을 때
`--test`는 `syntax check OK`를 출력했다. 실제 dnsmasq 기동은 Netlink 소켓
생성 실패로 종료되었으므로 DNS 서버 응답 시험으로 간주하지 않는다.

변경 후 로컬 단위·회귀 검사는 DNS 에이전트 70개 중 58개 통과·12개 건너뜀,
배포 검사 83개 중 81개 통과·2개 건너뜀이다. DNS에서 건너뛴 항목은 실제
dnsmasq/dig 통합 시험이고 배포에서 건너뛴 항목은 실제 nft 네임스페이스
시험이다. 캠페인 10개, 포털 6개, HTTP 데모 9개도 통과했다. HTTP 데모는
DNS 또는 HTTPS 통합 시험이 아니다.

다음 단계는 최신 커밋을 격리된 실제 Linux VM에 설치해 클라이언트의 UDP/TCP
질의, 정책 갱신·만료, 재부팅, 방화벽, 제거와 복구를 검증하는 것이다. 현재
CNAME 응답 체인과 DoH/VPN 우회는 이 변경으로 해결되지 않는다.
