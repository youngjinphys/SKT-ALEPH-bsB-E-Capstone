## 기준 및 판단

기준 HEAD는 `b6df712b76207ea53b38da09276b8e992f13ddd3`이다. 기존 로컬 Unix 수집 브리지, 클라우드 `/dashboard`, 독립 정책 서명·명시적 게시·장치 상태 보고의 경계는 유지한다. 수집 성공을 DNS 집행 성공으로 승격하거나, 프론트엔드 편의를 위해 웹 서버에 root·정책 개인키를 부여하지 않는다. 같은 화면을 두 번째 웹 프레임워크로 다시 만드는 대신 공유 콘솔과 클라우드 어댑터를 함께 검증했다.

## 화면과 조작

게시 대상 선택 → 서명 게시 파일 → 선택 노드 보고 → 규칙 → 전체 노드 순으로 정보 계층을 정리했다. 전체 노드 결과는 `확인한 수 / 등록 수`로 표시하며 한 장치의 성공을 전체 성공처럼 표현하지 않는다. 장치 등록은 키 지문을 확인하는 접이식 영역으로 분리했다. 긴 해시를 생략하지 않고 줄바꿈해 복사할 수 있게 표시한다. 반복되는 절차 설명 대신 선택 장치·보고 수신시각·정책 신원·DNS 비교 근거를 보여준다.

기존 네이비·시안 표면과 접근성 기반을 유지하되 상태 대비, 카드 간격, 단계 표기, 버튼 높이와 모바일 밀도를 조정했다. 기능별 스타일은 `console_deployment.py`에 한정했다. 사용자 이름·도메인·오류는 텍스트 노드로 렌더링하고 임의 HTML 삽입을 추가하지 않았다.

## 검증 기록

처음 작성한 세 회귀 테스트에서 전체 증거 context 누락, 키 없는 등록 해제 수락, 장치별 cloud 조회 404를 확인한 후 구현했다. 브라우저에서도 노드 조회에 503을 주입해 이전 정상 카드가 남는 실패를 확인했다.

로컬 검증: 정책 서버 107개 스위트를 root와 비특권 계정에서 각각 실행(권한별 경로는 의도적으로 다른 테스트가 skip), 클라우드 42개, JavaScript 15개가 통과했다. Node 22 환경에서는 TypeScript 테스트에 `--experimental-strip-types`가 필요했으며 원래 CI는 Node 24를 사용한다. 시스템 Python 경로가 필요한 정책 동기화 테스트는 `/usr/bin/python3`로 root/비특권 실행하여 통과했다. 테스트를 통과시키려고 root 실행 경로의 신뢰 검사를 약화하지 않았다.

공유 콘솔의 실제 로컬 HTTP 핸들러와 cloud ASGI/메모리 저장소에 대해 Playwright로 두 모드를 실행했다. 25개 검증 항목에는 동시 확인, 부분 장애와 복구, 늦은 대상 응답, 노드 검색, 등록 영역의 키보드 접근, 320/390/768px 반응형 및 로그아웃이 포함된다. 1440px 데스크톱과 모바일 화면을 캡처해 넘침·중복 ID·페이지 오류를 확인했다. Chromium에는 관리된 네트워크 제한을 우회하지 않는 loopback transport binding을 사용했다. 이것은 실제 운영 HTTPS·OAuth·Supabase 서비스에 대한 종단 간 증명이 아니다.

## 호환성 및 운영 인수

- 로컬 `intel/import`는 기존 필드에 `context_revision`을 추가해야 한다. 서버와 화면을 같은 커밋으로 갱신한 뒤 새로고침한다. 오래된 화면의 요청은 안전하게 거부된다.
- `nodes/unregister`와 cloud의 `nodes/remove` 별칭 모두 현재 표시한 `expected_key_id`가 필요하다. 키 없는 외부 스크립트는 갱신해야 한다.
- 대상별 deployment API는 읽기 전용이다. 선택은 DNS 주소·기본 장치·정책·게시 시퀀스를 수정하지 않는다.
- 신규 비밀 값, 공급자 호출, DB 마이그레이션, Vercel 환경 변수 변경, 실제 DNS 조작은 수행하지 않았다. 소스 스테이징용 일회성 워크플로는 반영 후 제거한다.
- 공급자 약관·실제 API 키·TLS·권한·재부팅·DNS/라우터/DoH·VLAN, 실제 LAN 단말 검증은 운영 환경에서 인수해야 한다. 성공한 로컬 노드 보고도 LAN 전체 보호를 입증하지 않는다.

## 동시 변경 보존 및 병합 재검증

반영 직전에 `main`이 `c6a72a1298ced9bf20baa7a026fadca7d8139090`으로 이동했다. 추가된 테스트 PIN 인증 변경 14개 파일은 그대로 보존했고, 겹친 `cloud/app.py`에서는 인증 라우트를 유지하면서 장치별 읽기 라우트만 병합했다. 병합 후 클라우드 51개 테스트(로컬 PostgreSQL 인수 2개는 환경상 skip), JavaScript 23개 테스트, 브라우저 25개 검증 항목을 다시 실행하여 통과했다. PIN을 켜거나 새로운 비밀값·운영 데이터베이스를 설정하지 않았으며, 해당 인증 변경을 이번 관제 디자인 작업의 신규 성과로 계산하지 않는다.
