# 기존 DNS 설치 전환·제거 검증 (2026-10-27)

Ubuntu 24.04.5 QEMU/KVM 격리 VM에서 Linux 6.8.0-147, systemd 255,
nftables 1.0.9, dnsmasq 2.91을 사용했습니다. DNS와 방화벽 변경은 VM 안에서만
수행했습니다. 실제 운영망과 물리 LAN의 가용성은 검증하지 않았습니다.

시험한 설치기 SHA-256은 `41b64f0e03ee70f9d7d6d620ef4402770d04b22310614d8914c684f09a9e3c1d`,
방화벽 도구 SHA-256은 `80bbe5e84e382118a66b7b936f7e5de2ba24bee7d5a9561696d27084893869c7`입니다.
동결 소스 tar와 게스트의 파일 해시를 대조했고 시험 종료 시 작업 트리도 다시 확인했습니다.

- `b47d7bb`: 원본 `root:root 0775` 소스에서 업그레이드·재시작·재부팅·제거,
  별도 설치의 직접 제거를 실행했습니다. 소유권 확인 옵션 누락과 외부 체인 추가는
  거부되며 기존 설정·DNS가 유지됐습니다. VM의 두 주소가 같은 veth 인터페이스를
  사용하도록 구성해 허용·비허용 클라이언트의 UDP/TCP를 확인했습니다.
- `e94665f`: 표식이 있고 코드 manifest가 없는 기존 설치의 업그레이드와 별도 직접
  제거를 실행했습니다. `f770f36`의 기존 설치도 업그레이드와 별도 직접 제거를 실행했습니다.
- 각 전환·제거 백업에서 기존 policy, state, active.conf의 바이트와 디렉터리 및 파일의
  숫자 UID/GID·모드를 대조했습니다. 재시작 후 state의 적용 시각은 갱신되지만 정책과
  설정 digest, 차단 수 및 시계 watermark는 의미상 유지되는지 확인했습니다.
- 방화벽 교체 후 `new-firewall` 단계에서 실제 SIGKILL을 주입했습니다. 재부팅 후
  서비스는 disabled/inactive였고 원본 정책·상태 및 검증된 백업이 남았으며 재전환은
  저널 때문에 거부됐습니다. 이 경우 자동 복구는 수행되지 않아 DNS는 중단 상태였습니다.
  다른 모든 중단 지점이나 실제 정전의 결과로 일반화하지 않습니다.
- 원격에서 가져온 `f770f36`은 0775 소스에서 신규 설치에 실패했습니다. 정상적인 기존
  설치를 구성하기 위한 별도 시험에서는 VM 안의 소스 모드만 0755로 바꿨습니다. 수정된
  새 코드는 0775 소스에서 신규 설치·제거에 성공했습니다.

구버전 `b47d7bb`는 이 VM의 dnsmasq가 요구하는 AF_NETLINK를 unit에서 막으므로 원본
그대로의 첫 설치가 실패했습니다. 운영 중인 레거시를 재현할 때만 VM 전용 drop-in으로
초기 시작을 허용하고, 이후 drop-in을 제거하고 daemon-reload했습니다. 원본 unit과
firewall 파일은 생성기의 출력과 바이트 단위로 비교했습니다. 따라서 이 기록은 구버전이
해당 VM에서 보정 없이 처음부터 부팅된다는 증거가 아닙니다. 재부팅 직후 준비되기 전의
SSH 접속 실패 및 재시도 성공도 원문에 남겼습니다.
