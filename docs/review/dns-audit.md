# DNS 및 프로젝트 검토

검토일: 2026-10-25. 출발점은 `Frontend` 커밋과 Notion의 김다영님 제출 코드입니다.
이 문서는 **소스 사실, 구현 선택, 시험 결과, 아직 합의하지 않은 요구**를 구분합니다.

## 판단

목록 기반 DNS 집행은 구현·시연 가능한 방어 수단이지만, 새 피싱 탐지 알고리즘이나
피해 예방률을 자동으로 증명하지 않습니다. 프로젝트의 현재 의의는 정책의 검증·적용·철회·실패 복구를
재현하고 보호 범위를 설명하는 데 있습니다. 원격 수집·AI 모델·사용자별 예외 기능은 별도 검증해야 합니다.
**교육 평가가 AI 기능을 요구하는지는 공식 기준을 확인해야 합니다.** DNS 단독 실험이 가능하다는 이유로 AI를 최종 제출에서 생략해도 된다고 결론내리지 않습니다.

## 구현 선택과 대안

제출된 dnsmasq를 유지해 검증 범위를 좁혔습니다. 이는 팀이 dnsmasq를 운영 엔진으로 합의했다는 뜻이 아닙니다.
Unbound/BIND RPZ는 이름 매칭·응답 체인 등 요구가 생겼을 때 비교할 대안이며, 기존 미검토 지침을 채택 근거로 사용하지 않았습니다.
QNAME의 정확 매칭과 “어떤 캐시에서도 하위 이름은 영향받지 않음”은 다릅니다. RFC 8020의 NXDOMAIN cut도 고려해야 합니다.
`address` 설정을 바꾸고 SIGHUP만 보내면 일반 설정 파일이 재로딩되지 않으므로, 현재는 소유한 실험 프로세스를 교체합니다.
향후 `servers-file` 기반 갱신이나 별도 리졸버 전환은 무중단·성능 요구와 함께 평가할 수 있습니다.

## 시험과 한계

- `python3 -m unittest discover -s apps/dns-agent/tests -v`: 입력·CLI·실제 임시 디스크의 트랜잭션·실패 주입·DNS 패킷 검사.
- 실제 dnsmasq+dig 시험은 6개입니다. 로컬 검토 환경에는 두 바이너리가 없어 skip되며 **통과가 아닙니다**.
- `REQUIRE_DNSMASQ=1`의 CI에서는 바이너리 부재를 실패로 처리합니다. 해당 커밋의 Actions 로그에서 실제 실행을 확인해야 합니다.
- 프론트엔드 정적 테스트 6개는 통과했습니다. 원작 파일과 public UI는 이 변경에서 수정하지 않습니다.
- 실패 주입은 잘못된 갱신·복구 실패·저널 중단·설정 불일치·만료 후 복원을 검사합니다. 전원/파일시스템 손상과 모든 네트워크 조건을 증명하지 않습니다.

[잔여 위험](../threat-model.md): 운영 LAN/53번 배포, 원격 인증/서명, DNSSEC, CNAME/HTTPS 응답 체인,
클라이언트 캐시·외부 DNS/VPN, 사용자별 WARN 예외, 실제 신고 API·HTTPS 배포, ML 평가는 별도입니다.

## 추가 확인한 신뢰성 경계

- **건강 응답 검사의 결함 재현:** 원래 검사기는 응답에 ANCOUNT=1을 기록하고 본문에 임의 1바이트만 붙인 가짜 패킷도 정상이라고 받아들였습니다. 현재는 답변 이름·유형·클래스·길이·기대 IPv4/IPv6 데이터를 모두 검사합니다. 그러나 로컬 리스너의 답변만 확인하므로 원격 업스트림 가용성을 보증하지 않습니다.
- **정책 메타데이터만 변경 시 DNS 재시작 회피:** 실제 차단 설정이 그대로라면 상태만 저널로 원자적으로 기록합니다. 상태 기록에 실패하면 이전 상태를 복구하며 DNS 리스너는 유지합니다.
- **시계 역행:** 재시작 전 마지막으로 기록한 적용시각을 하한으로 삼아, 이미 제거한 만료 차단이 재시작 후 시계 역행만으로 복구되지 않도록 합니다. 단, 기록되지 않은 오프라인 기간의 절대 시각은 보장할 수 없습니다.
- **CNAME 한계 검증 강화:** 기존 테스트의 'NOERROR 또는 NXDOMAIN이면 성공'을 제거하고, 통제된 별칭에서 실제 CNAME과 차단된 이름의 A 레코드가 반환된다는 반례를 명시적으로 검사합니다. 이는 보호 성공이 아니라 보호 범위의 공백을 나타냅니다.

## 추가 장애 검토 (2026-10-26)

- **준비 단계 오류와 실제 적용 오류를 분리:** 이전 구현은 `candidate.conf` 또는 `pending.json` 기록 실패가 `OSError`로 상위 루프까지 전파되어, 이미 정상 작동하던 소유 DNS를 종료시킬 수 있었습니다. 전환 전 단계는 `ApplyError`로 거부하고 기존 프로세스를 유지하며, 만료된 차단을 제거할 수 없는 경우만 기존의 치명적 보호 경계를 적용합니다. 두 준비 실패와 만료 후 실패에 대한 회귀 검사를 추가했습니다.
- **프로세스 생존 ≠ 질의 응답:** 기존 코드는 프로세스가 살아 있으면 설정 변경 없이 그대로 둡니다. 현재는 단조 시계 기반으로 약 5초 간격으로 로컬 A/AAAA 건강 답변과 대표 차단 카나리아를 검사하고 실패 시 소유 프로세스를 재시작·검증합니다. 이는 업스트림·전체 규칙·실제 클라이언트의 가용성 검증이 아닙니다.
- **작업 계약은 아직 팀 미승인:** `BLOCK/WARN/ALLOW` 및 `SUBTREE`는 로컬 격리 실험 구현입니다. 실제 원격 공급자의 정책 서명, 사용자별 WARN UX와 운영 DNS는 팀 리뷰 후 결정해야 합니다.

## 저장 정책·복구 저널의 일관성 재점검 (2026-10-26)

- **누락된 정책 해시 검증:** 기존 구현은 활성 DNS 설정과 `config_sha256`은 대조하지만, 저장된 정책 문자열과 `policy_sha256`의 일치는 검사하지 않았습니다. 이 때문에 저장 정책 일부가 변경되어도 다음 적용 후보로 채택될 수 있었습니다. 활성 상태 조회뿐 아니라 중단된 작업의 저널 복구에서도 정책·설정 해시를 함께 확인하도록 수정했습니다. 파일이 손상되면 자동 적용·복원을 거부하며, 손상 감지는 **발행자 인증이 아닙니다**.
- **크기 팽창:** UTF-8 원본 입력이 1 MiB 이하여도 JSON ASCII 이스케이프 이후 저장 정책은 더 커질 수 있습니다. 이는 상태 조회 한도를 넘어 재시작 복구를 실패시킬 수 있으므로 정규화 결과에도 1 MiB 상한을 적용합니다.
- 서로 다른 실패 경로의 회귀 시험을 추가했습니다. 동일 로컬 계정이 파일과 해시를 함께 위조하는 경우, 모든 전원·파일시스템 장애, 원격 정책 신뢰는 별도 보호 과제입니다.

## 평가를 혼동하지 않는 방법

기능 시험과 탐지 성능 평가를 분리합니다. 기능 시험은 정상 응답이 있는 통제된 `.test` 이름에 정책을 적용·철회해 비교합니다.
탐지 평가는 출처·라벨·시간/도메인/캠페인 분할, TP/FP/FN/TN, precision/recall/FPR, 기저율이 필요합니다.

가정 예시(실측 아님): 악성 비율 0.1%, TPR 99%, FPR 1%이면
`precision = p*TPR / (p*TPR+(1-p)*FPR) = 11/122 ≈ 9.0%`입니다.
정상 독립 표본 10개에서 오탐 0건이어도 오탐률의 단측 95% 상한은 `1-0.05^(1/10) ≈ 25.9%`입니다.
같은 캠페인의 상관된 샘플에는 이 독립 이항모형을 그대로 적용할 수 없습니다.
Wolfram의 유리수·지수 계산과 Python 재계산으로 수치를 확인했으며 제품 성능 수치가 아닙니다.
