# nftables 격리 VM 검증 기록

2026-10-27에 공식 Ubuntu 24.04.5 cloud 이미지를 QEMU/KVM에서 실행했습니다.
이미지 SHA-256 `04e8f2461a16a44e78a370284471f29616cdd9baf1893df25807b71f985b6c94`은
공식 SHA256SUMS와 일치했습니다. 게스트는 Linux 6.8.0-147,
systemd 255, nftables 1.0.9, dnsmasq 2.91이었습니다. 운영 호스트의 DNS,
방화벽 및 systemd 설정은 시험에 사용하지 않았습니다.

시험한 설치기 SHA-256은 `0358ffec9bc9d16479e77db61aa596a9b6871c3fcf74ecb8faf7cf19b6500299`,
방화벽 도구 SHA-256은 `05bc796f9d92f30b97becca41d3a350d89f17535de8944b643ccff8a3ce97b9a`입니다.
게스트와 작업 트리의 파일 해시를 종료 시 다시 비교했습니다.

- 실제 systemd 설치와 서비스 재시작, 게스트 재부팅 후 서비스·방화벽 복구를 확인했습니다.
- VM 내부의 별도 네트워크 네임스페이스에서 같은 veth 인터페이스로 접근했습니다.
  `192.168.44.20`은 허용하고 `192.168.44.200`은 거부했습니다. UDP/TCP별로
  승인된 BLOCK의 NXDOMAIN, 정상 이름의 통제 업스트림 `192.0.2.42` 응답,
  비허용 클라이언트의 timeout을 재부팅 전후 확인했습니다.
- 새 빈 정책을 발행한 뒤 BLOCK 이름이 통제 업스트림의 양성 응답으로 복구됐습니다.
- 소유권 표식을 복제한 추가 규칙이 있을 때 재시작과 제거가 실패하고 테이블이
  유지됐습니다. 추가 규칙 제거 후 정상 제거, 전용 테이블·디렉터리 부재 및
  정책·상태 백업을 확인했습니다.
- 설치 전 동명 외부 테이블을 보존했습니다. 서비스 시작 실패를 주입해 정상 롤백을,
  실패 직전 외부 테이블로 교체해 롤백 중단과 외부 테이블·설치 자료 보존을 확인했습니다.
- root 실행의 필수 네임스페이스 시험 7개가 통과했습니다. 최초 시도는 root 사용자
  네임스페이스에서 모드 0700 홈을 읽지 못해 실패했습니다. 이후 root는 네트워크
  네임스페이스만 사용하도록 시험을 수정하고 원래 경로에서 다시 실행했습니다.
  소스 복사 시에도 이전 root 소유 `__pycache__` 제거 권한 오류가 기록됐으므로,
  실행에 사용한 소스 파일은 복사 후와 종료 시 SHA-256을 각각 대조했습니다.

[원문 로그 묶음](evidence/nft-vm-20261027.tar.gz)의 SHA-256은
`1dc1cbdaac611e810d67f5ab09943af3d3fc3dbc37a66c7769eaa5d3a7624027`입니다.
실패 주입 로그의 오류는 의도한 시험 결과이며, 최초 네임스페이스 시험 실패도 보존했습니다.
**검증 대상 구분:** 위 VM 결과는 본문에 명시한 설치기와 방화벽 도구의 SHA-256에 대해서만 유효합니다. 이후 변경된 최신 HEAD의 설치·제거 및 상태 복구를 그 VM에서 다시 검증한 자료가 아닙니다. 최신 GitHub Actions의 격리 nftables 네임스페이스 시험은 VM 내 systemd 설치→정책 게시→재부팅→제거와 다르므로, 최신 SHA로 완전한 통합 실험을 다시 수행해야 합니다.
실제 물리 LAN, 운영 서버의 방화벽 공존·성능 및 다른 커널 전체를 입증하지는 않습니다.
