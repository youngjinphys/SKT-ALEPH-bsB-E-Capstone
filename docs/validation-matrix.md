# 조건별 검증표와 완료 기준

이 문서는 실행 가능한 시험과 앞으로 필요한 시험을 구분합니다. 시험 개수는 탐지 정확도나 피해 예방률이 아닙니다.
현재 수명주기 구현은 **검토된 로컬 정책을 사용하는 협조적 클라이언트 경로**가 대상입니다.

## 현재 자동화한 범위

| 질문 | 대조 조건과 기대 결과 | 증거 위치 |
| --- | --- | --- |
| 원래 응답할 이름을 차단했는가? | 통제 업스트림에서 양성 A/AAAA를 먼저 확인; BLOCK 및 하위 이름은 NXDOMAIN | `apps/dns-agent/tests/test_integration.py` |
| 다른 정상 이름은 통과하는가? | ALLOW/WARN 및 비대상 유사 이름은 원래 fixture 주소 유지 | 같은 통합 시험 |
| 전송·질의 종류에 일관적인가? | UDP/TCP와 A/AAAA/HTTPS 질의를 개별 확인 | 같은 통합 시험; IPv6 전송 시험과 구분 |
| 잘못된 갱신 중에도 만료되는가? | 잘못된 입력은 거부; 파일 부재 상태에서도 유효기간 경과 후 기존 차단 제거 | 통합·transaction 시험 |
| 오탐 철회를 적용할 수 있는가? | 발행시각이 더 새로운 빈 정책을 적용해 fixture 주소 복원 | 통합·transaction 시험 |
| 장애 복구가 가능한가? | 후보/저널 기록 오류·기동 실패·실행 중 무응답·저널 손상별 기대 동작 확인 | transaction·wire 시험 |
| CNAME 체인을 차단하는가? | `alias.test → blocked.test`와 주소가 반환되는 **한계 재현** | `test_alias_is_outside_qname_block_guarantee` |
| 캠페인별 가상 정책이 적용 계약과 일치하는가? | 4개 캠페인 11개 규칙 중 실습 승인 BLOCK 4개만 렌더링, WARN·ALLOW·미승인 BLOCK 비차단, 그룹 중복·변조 입력 거부 | `tests/policy/test_campaign_policy.py` (실행 후 CI 기록 확인) |
| HTTP 안내는 실제 정책에 따라 분기되는가? | 명시적 실습 DNS A 매핑과 `BLOCK/WARN` Host별 302→기존 정적 포털; 비승인·만료·변조 상태는 거부 | `apps/dns-agent/tests/test_integration.py`, `tests/e2e/test_http_policy_notice.py` |

CI는 `.github/workflows/dns.yml`에서 실제 dnsmasq·dig를 설치하고 `REQUIRE_DNSMASQ=1`을 설정합니다.
실제 DNS 시험의 skip은 통합 통과가 아닙니다. HTTP 고포트 테스트는 DNS 응답·302 경로를 분리해서 검증하며, 실제 LAN 53/80 배포나 HTTPS 사용자 경험의 증거가 아닙니다.
CI URL과 소스 SHA는 발표 직전에 같은 커밋을 가리키는지 대조합니다.

## 남은 실험과 판정

| 조건 | 필요한 실험 | 완료 기준 |
| --- | --- | --- |
| 팀의 격리 VM | 동일 소스·바이너리 버전으로 재실행 | skip 없는 DNS 시험과 원문 DNS 응답 보관 |
| 실제 LAN·IPv4/IPv6 | 승인된 별도 실습망에서 DHCP/RA 및 DNS 경로 확인 | 두 주소 체계에서 사용된 리졸버·정책 적용 범위 기록 |
| 외부 평문 DNS | 지정 보호 DNS와 다른 리졸버를 조건별로 비교 | 허용된 경로에서 우회 여부 기록; 미차단을 실패 은폐하지 않음 |
| DoH·DoT·VPN | 관리 여부·전송 경로를 명시한 비교 | 각 조건의 실제 리졸버와 통신 결과 확인; 포트 차단만으로 완전 통제를 주장하지 않음 |
| 캐시·연결 재사용 | 정책 적용 전후 캐시와 연결 상태 통제 | 새 DNS 질의와 기존 연결 결과를 분리 기록 |
| CNAME·HTTPS/SVCB 체인 | 응답 체인을 검사하는 엔진 대안 비교 | 양성·차단·복합 별칭 fixture별 적용 범위를 명시 |
| HTTPS 안내 | 실습 DNS A 변경과 HTTPS 인증서 검증의 차이를 확인 | 원래 HTTPS 탭에서 자동 안내되지 않고 연결 오류가 발생할 수 있음을 명확히 전달 |
| 업스트림 장애 | 로컬 리스너 건강과 외부 이름 해석을 따로 확인 | 장애 알림·운영 판단 조건과 허용 중단시간 합의 |
| 원격 정책 공급 | HTTPS 정적 파일·Ed25519 서명·장치 ID·버전·만료·수신/적용 역할 분리 | `tests/policy_sync/`: 루프백 TLS·304·서명 위조·버전 역행·빈 목록 철회·발행 실패. 실제 192.168.7.69 설치 및 재부팅 검증은 별도 |
| 공공·ISP 협력 | 책임 주체와 연계 범위를 검토 | IOC 제공·검토·집행·이의신청·철회 역할을 분리한 제안; 제휴 확정과 구분 |

## 지표의 분모를 먼저 고정

- **정책 집행 성공률:** 기대 결과와 일치한 질의 수 / 동일 fixture·경로에서 실행한 유효 질의 수. 질의 종류·전송·캐시 상태별로 분리합니다.
- **정상 도메인 영향:** 별도 정상 대조 집합에서 의도치 않게 차단된 도메인 수 / 시험한 정상 도메인 수. 합성 데이터 결과를 실제 서비스 오탐률로 일반화하지 않습니다.
- **적용·철회 지연:** 입력 교체 또는 승인 시점부터 첫 기대 응답 확인까지. 여러 번 측정한 중앙값·95백분위수와 최대값을 기록합니다.
- **가용성:** 정상 대조 질의의 응답 성공 수 / 보낸 정상 질의 수. NXDOMAIN·SERVFAIL·timeout을 구분하고, 로컬 리스너와 업스트림 장애를 분리합니다.
- **우회 조건:** 서로 다른 경로를 단일 '우회 방지율'로 합치지 않습니다. 관리 단말 여부·리졸버·DoH/DoT/VPN·IPv6·캐시 조건마다 결과를 표시합니다.
- **IOC 탐지 성능:** 출처가 확인된 라벨·시간 분할·중복/캠페인 누수 통제를 갖춘 별도 평가가 있어야 precision/recall을 주장합니다. 현재 수치 없음.

공공의 위협정보 공급과 ISP 배포는 목록 품질·갱신 속도·기본 보호 범위를 개선할 수 있다는 **제안**입니다.
실제 개선은 같은 정책을 지역 실험과 운영 가능한 경로에서 비교해야 하며, 협력만으로 TLS 인증·외부 VPN·미등록 피싱 문제가 해결되지는 않습니다.
